# 面接準備ガイド（社内備品貸出管理システム）

> これは本人の面接準備用メモです。README からは敢えて目立たせていません。
> 面接では「このプロジェクトで実際にどう書いたか」を必ず添えて話します。

---

## 1. 30 秒で説明

> 「Spring Boot で社内備品の貸出管理システムを作りました。
> 単純な CRUD ではなく、**貸出中の備品は貸せない**・**承認は管理者だけ**・**不正な状態遷移を防ぐ**といった
> 業務ルールを実装しています。
> 特に力を入れたのは、同じ備品に同時に申請が来ても 1 件しか通らないことで、
> 備品の行を悲観ロックしてから確認する形にし、10 スレッドで同時に叩くテストで検証しました。
> テストは 37 件で、Docker がなくても `./mvnw test` で完走します。」

## 2. 1 分で説明

> 「構成は Controller → Service → Repository → Entity の 4 層です。
> Controller は HTTP の入出力だけ、Service がトランザクション境界と権限チェック、
> Entity に**状態遷移のルールそのもの**をメソッドとして持たせています。
> `returnAsset()` は APPROVED 以外から呼ばれると例外を投げるので、
> 『返却済みをもう一度返却する』というバグが構造的に起きません。
>
> DB は PostgreSQL で、スキーマは Flyway で管理し、起動時に `ddl-auto=validate` で
> エンティティとのズレを検出します。貸出（loan）と履歴（loan_history）を分けていて、
> 『今の状態』と『いつ誰が何をしたか』を別々に持っています。
>
> 二重貸出の防止は、申請時に備品の行を `SELECT ... FOR UPDATE` でロックしてから
> 重複を確認する方式です。素朴に『確認してから登録』だと同時実行で両方通ってしまうので、
> 実際に 10 スレッドで同時申請するテストを書いて、成功が 1 件だけになることを確認しています。
>
> エラーは RFC 9457 の Problem Details 形式で返し、`code` で分岐できるようにしました。」

## 3. 開発背景

- 業務システムでは「画面を作る」より**業務ルールを壊さない**ほうが難しく、そこが評価されると考えた
- 備品貸出は題材として身近で、実際に運用すると起きる事故（二重貸出・不正遷移・権限漏れ・履歴欠落）が具体的に想像できる
- 自分の経験（データ分析・Python）に対して、**業務系 Java の基礎**を示す作品がなかった
- 「なぜこの設計にしたか」を説明できる状態にするため、過剰な抽象化は避けた（Lombok も入れていない）

## 4. Architecture

```
Controller（HTTP の入出力・DTO 変換）
    ↓
Service（トランザクション境界・権限チェック・業務判断）
    ↓
Repository（Spring Data JPA・検索条件・ロック）
    ↓
Entity（状態遷移のルールと不変条件）
```

- **なぜ 4 層か**: 責務が違うものを混ぜると、テストが書きにくくなる。
  Service のテストはリポジトリを Mock にすれば DB なしで速く回せる
- **Entity にルールを置く理由**: 状態遷移はどの層から呼ばれても守られる必要がある。
  Service に書くと「別の Service から呼んだときに守られない」リスクが出る
- **DTO を返す理由**: ①遅延ロードの罠を避ける ②DB の構造がそのまま API 仕様になるのを防ぐ

## 5. 技術選定理由

| 選んだもの | 理由 | 代替案を選ばなかった理由 |
|---|---|---|
| Java 21 | LTS。`record` を DTO に、`switch` 式を例外→HTTP ステータスの分岐に使える | Java 17 でも動くが、record と switch 式でコードが短くなる |
| Spring Boot 3.5 | MVC + JPA + Validation + Security を最小構成でまとめられる | 素の Servlet は学習コストに見合わない。日本の業務系で最も使われている |
| PostgreSQL | 業務系で最も一般的。標準 SQL（IDENTITY など）で書ける | H2 だけだと「本番と違う DB でしかテストしていない」ことになる |
| Flyway | スキーマをコードとしてレビューできる。`ddl-auto=update` は本番で使うべきでない | `ddl-auto=update` は変更履歴が残らず、レビューできない |
| Maven（Wrapper 同梱） | `./mvnw` だけで同一バージョンが動く。設定が宣言的 | Gradle でも良いが、`pom.xml` のほうが「何を依存しているか」が一覧で読みやすい |
| H2（PostgreSQL 互換モード）をテストに | Docker なしで誰でも `./mvnw test` できる | Testcontainers は Docker 必須。**将来は併用したい**（Limitations に記載） |
| **Lombok を入れない** | 面接でコードを読んでもらう前提。`getter` を明示すると「何が起きているか」が一目で分かる | Lombok は便利だが、アノテーションが増えると初学者には読みづらい |
| **MapStruct を入れない** | 変換箇所が少なく、`DtoMapper` 1 クラスで十分読める | 自動生成コードは面接で説明しづらい |

## 6. 一番苦労した点

**二重貸出を「本当に」防ぐ方法。**

最初は「申請時に貸出中の貸出があるか確認して、無ければ登録」という素朴な実装にしました。
テストは通りましたが、**同時実行では壊れます**。2 つのリクエストが両方チェックを通過して、
両方登録されてしまうからです。

対策として、申請時に備品の行を悲観ロック（`SELECT ... FOR UPDATE`）してから確認するようにしました。
さらに、`@Version` による楽観ロックも併用しています。

本当に効いているかを確かめるため、**10 スレッドで同時に申請するテスト**を書き、
成功が 1 件・残りは 409 になることを確認しました。
「テストが通った」ではなく「同時実行でも壊れない」を確かめたのがこのプロジェクトで一番苦労した点です。

さらに、H2 と PostgreSQL でロックの SQL が違うという問題にも当たりました（後述）。

## 7. 発生したバグ（実際のもの）

1. **H2 が `FOR NO KEY UPDATE` を解釈できず、結合テスト 8 件が全滅**
   PostgreSQL 方言を指定していたため、悲観ロックが PostgreSQL 固有の構文に変換されていました。
2. **`LazyInitializationException` で一覧 API が 500**
   `open-in-view=false` の状態で、トランザクション外の DTO 変換が遅延ロードを踏んでいました。
3. **管理者が存在せず初期データ投入が全滅（404）**
   管理者を登録する API 自体が管理者権限を要求する鶏卵問題。
4. **`*IT` がテストとして実行されていなかった**
   Maven Surefire の既定パターンに `*IT` が含まれず、書いた結合テストが無視されていました。
5. **貸出履歴のある備品が物理削除できてしまう**
   履歴テーブルから参照できないデータができる寸前でした。

## 8. どう解決したか

| バグ | 原因 | 対処 |
|---|---|---|
| H2 で `FOR NO KEY UPDATE` | PostgreSQL 方言をテストでも使っていた | テストプロファイルで H2 方言を明示。理由をコメントに残す。`LOCK_TIMEOUT` も延長 |
| `LazyInitializationException` | `open-in-view=false` + 遅延ロード | `@EntityGraph` でレスポンスに必要な関連を先読み。「レスポンスで使う関連はリポジトリで宣言する」ルール化 |
| 初期データ投入が 404 | 鶏卵問題 | ①ヘッダの社員が未登録なら自動登録 ②初期管理者は Flyway で投入 |
| `*IT` が実行されない | Surefire の既定 include パターン | `pom.xml` に `**/*IT.java` を追加。テスト件数を必ず確認する習慣に |
| 履歴のある備品が消せる | 削除時のチェック漏れ | 削除 API で 409 を返し、`RETIRED`（廃棄）へ誘導。テストで固定 |

## 9. 改善するとしたら何をするか

1. **Spring Security + OIDC で認証**（今はヘッダで操作者を渡すデモ用の割り切り）
2. **Testcontainers で PostgreSQL の結合テスト**（ロックの挙動を本番と同じ条件で検証）
3. 将来日付の**予約**機能（貸出期間の重複チェックと排他制約）
4. 延滞の**自動検出バッチと通知**（メール / Slack）
5. OpenAPI（springdoc）で API 仕様を自動生成し、フロントエンドと共有

## 10. 技術質問と回答

### Java / OOP

**Q. カプセル化をこのプロジェクトでどう使いましたか。**
A. エンティティのフィールドはすべて `private` にし、状態を変える操作を**意味のあるメソッド**に限定しました。
例えば `Asset.status` を直接 setter で変えられるようにせず、`markLoaned()` / `markAvailable()` /
`changeStatus()` だけを公開しています。setter を公開すると「貸出中なのに AVAILABLE にする」といった
不正な状態を外から作れてしまうためです。

**Q. 継承より委譲を選んだ場面は。**
A. 例外クラスは共通の `BusinessException` を継承していますが、**業務ロジックには継承を使っていません**。
`LoanService` と `AssetService` は共通の基底クラスを持たず、それぞれが必要なリポジトリを
コンストラクタで受け取る形にしています（継承で共通化すると、片方の変更がもう片方に影響するため）。

**Q. `record` をどこで使いましたか。**
A. DTO（リクエスト・レスポンス）です。不変で、`equals`/`hashCode`/`toString` が自動生成されるため、
テストや API の出力で扱いやすいからです。エンティティには使いません（JPA は可変である必要があるため）。

**Q. `var` は使いますか。**
A. テストコードでは使っていますが、本体では型を明示しています。
面接でコードを読む人が「何の型か」をすぐ判断できるほうが良いと考えました。

### Spring / Spring Boot

**Q. DI コンテナの利点は何ですか。**
A. 依存関係を自分で `new` せず、フレームワークが組み立ててくれるため、
テスト時にモックへ差し替えられます。実際 `LoanServiceTest` では
リポジトリ 4 つを Mockito のモックに差し替えて、DB なしで業務ルールを検証しています。

**Q. コンストラクタインジェクションを使う理由は。**
A. ①`final` にできるので不変 ②必須依存が明確 ③テストで `new` しやすい、の 3 点です。
フィールドインジェクション（`@Autowired` をフィールドに付ける）は、テストでリフレクションが必要になり避けています。

**Q. `@Transactional` をどこに付けましたか。読み取り専用は。**
A. クラスに `@Transactional(readOnly = true)` を付け、更新メソッド（`requestLoan` / `approve` / `returnAsset` など）
に `@Transactional` を重ねています。読み取り専用を既定にすると、
意図しない更新を防げて、DB 側の最適化も効きます。

**Q. `open-in-view` を false にした理由は。**
A. デフォルトの true は「リクエストの間ずっと DB セッションを開いたまま」にする設定で、
意図しない遅延ロード（N+1）を隠してしまいます。false にして、
必要な関連は `@EntityGraph` で明示的に読む形にしました。副作用として遅延ロードが例外になるので、
**問題が早期に可視化される**という利点もあります。

**Q. Spring Security を入れているのに認証していないのはなぜですか。**
A. デモの焦点は業務ルールだからです。設定で全リクエストを許可し、
操作者はヘッダから解決しています。権限チェック（管理者か）はサービス層で毎回行うので、
ヘッダを偽装しても管理者操作はできません。本番では OIDC に置き換える想定で、
その置き換え箇所を 2 クラスに閉じています。

### MVC / REST

**Q. Controller にビジネスロジックを書かない理由は。**
A. ①テストが書きにくい（HTTP の準備が必要）②複数の入口（バッチ・別 API）から同じ処理を呼べない、
の 2 点です。このプロジェクトでは Controller は `@Valid` と DTO 変換だけを行い、
判断はすべて Service に置いています。

**Q. REST のステータスコードはどう選びましたか。**
A. 400（入力形式の誤り）、403（権限がない）、404（対象が存在しない）、409（今の状態と矛盾する）を使い分けました。
特に **409 を丁寧に使う**のを意識していて、
「貸出中の備品に申請」「返却済みを再返却」「管理番号の重複」はすべて 409 です。
リクエストの形式は正しいが状態と矛盾する、という区別です。

**Q. Problem Details（RFC 9457）を使った理由は。**
A. エラーの形を統一すると、クライアントが機械的に分岐できます。
`type`/`title`/`status`/`detail` に加えて `code`（`INVALID_STATE` など）を返すので、
メッセージの文言を変えてもクライアントの分岐が壊れません。バリデーションエラーは `errors` に項目別に入れています。

**Q. バリデーションはどこで行いますか。**
A. 形式の検証は `@Valid` + Bean Validation（DTO）、**業務ルールの検証は Service** です。
「必須項目が空」は形式の問題、「貸出中は申請できない」は業務ルールなので、置き場所が違います。

### SQL / JPA

**Q. N+1 問題とは何で、このプロジェクトではどう対策しましたか。**
A. 一覧を 1 クエリで取った後、各行の関連を個別に取得して N+1 回のクエリが走る問題です。
このプロジェクトでは `@EntityGraph` で関連を JOIN FETCH し、
貸出一覧・備品検索のいずれも固定回数のクエリで済むようにしました。
`open-in-view=false` なので、遅延ロードのままなら例外になり、見落としません。

**Q. 悲観ロックと楽観ロックの使い分けは。**
A. このプロジェクトでは**両方**使っています。
- **悲観ロック**（`SELECT ... FOR UPDATE`）: 二重申請の防止。競合が実際に起きる箇所で、
  確実に直列化したい
- **楽観ロック**（`@Version`）: 同じ備品・貸出の同時更新の検出。衝突したら 409 を返して再実行を促す

楽観ロックだけだと「両方が読んで、両方が書く」を防げないため、二重貸出の防止には悲観ロックが必要です。

**Q. インデックスはどこに張りましたか。**
A. `asset.status`（貸出可能な備品の検索）、`loan(requester_id, status)`（自分の貸出一覧）、
`loan(asset_id, status)`（重複申請の判定）、`loan(status, due_on)`（延滞一覧）です。
実際に発行されるクエリの WHERE 句に合わせています。

**Q. `ddl-auto=validate` にした理由は。**
A. Hibernate にスキーマを作らせると、変更履歴が残らず、本番との差分も見えません。
Flyway で SQL を管理し、`validate` でエンティティとの不一致を**起動時に検出**する形にしました。
実際にこの設定のおかげで、カラムの追加忘れに早く気づけました。

**Q. 履歴テーブルを別に持つ理由は。**
A. `loan` は「今の状態」を持ち、`loan_history` は「いつ誰が何をしたか」を持ちます。
1 つのテーブルに両方を詰め込むと、状態の更新で過去の記録が上書きされてしまいます。
履歴は追記のみ（更新・削除しない）というルールにしています。

### テスト

**Q. テストをどう層別しましたか。**
A. ①ドメイン（状態遷移のルール、Spring 起動なし）②サービス（Mockito でリポジトリを差し替え）③結合（実 DB）
④API（MockMvc）の 4 種です。下の層ほど速く、失敗原因が特定しやすいので、
「ルールはドメインのテストで固定し、API のテストは HTTP の契約に絞る」という分担にしています。

**Q. 同時実行のテストはどう書きましたか。**
A. `ExecutorService` で 10 スレッドから同じ備品に申請し、成功件数が 1 件、
残りが `DuplicateRequestException` になることを検証しています。
各スレッドが独立したトランザクションで動くので、ロックが効いていなければ複数成功して落ちます。

**Q. テスト用 DB に H2 を使うリスクは。**
A. SQL の方言差です。実際に悲観ロックの構文が違い、テストが全滅しました。
「テストが通るから本番も大丈夫」とは言えず、
**Testcontainers で PostgreSQL を使う結合テストを追加したい**と考えています（Limitations / Future Work）。

**Q. テストが実行されていることをどう確認しましたか。**
A. テスト件数です。`*IT` が Surefire の対象外で実行されていなかったことに気づいたのは、
「書いたはずのテストより件数が少ない」と気づいたからでした。以降は実行ログの件数を必ず見ています。

### Docker / 運用

**Q. Docker 化の利点は。**
A. 「Java 21 を入れて、PostgreSQL を用意して…」という手順を `docker compose up` に畳めることです。
面接官や他のエンジニアが**同じ環境を 1 コマンドで再現**できるのは、レビューのコストを下げます。

**Q. 本番で気をつけることは。**
A. ①DB のパスワードを環境変数で渡す（`application.properties` に書かない）
②`ddl-auto` は `validate`、スキーマ変更は Flyway
③Flyway のマイグレーションは**後から書き換えない**（適用済みのチェックサムが変わり起動できなくなる）
④`open-in-view=false`、⑤ログに個人情報を出さない、あたりです。
このプロジェクトは Dockerfile で非 root ユーザーで実行するようにしています。

**Q. マイグレーションを後から書き換えてはいけない理由は。**
A. Flyway は適用済みマイグレーションのチェックサムを記録しており、
書き換えると検証エラーで起動できなくなります（あるいは環境ごとにスキーマがずれます）。
変更は必ず新しいバージョン（V3, V4…）として追加します。
